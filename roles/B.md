# 파트 2 섬과 캐릭터 게임

목표는 도착이 실제 저장된 성장·기념품으로 바뀌고, 꾸미기 결과가 섬과 동행 화면에 같게 보이도록 만드는 것이다. 게임 상태의 유일한 작성자는 B다.

## 읽을 것

AGENTS, docs/03·04·05·06·09·15, contracts, content/catalog.json, fixtures의 arrival와 UI 샘플, tasks/backlog의 B01~05.

## 작업 순서와 산출물

1. B01: 기본 GameSnapshot과 단일 GameService·DataStore 인스턴스를 만든다. Loading·읽기 실패를 초기 상태와 구분한다.
2. B02: 먼저 한 캐릭터·한 지역으로 보상과 원본 영수증을 원자 저장한다. 같은 ID·같은 날짜·재방문·실패를 작은 시험으로 확인한다. A의 SDK 완료를 기다리지 않는다.
3. B03: 섬과 인벤토리에서 GameAction만 사용해 의상·음식·장식을 적용한다. 음식 연출은 성공 결과 이후의 일시 UI 상태다. 장식은 3슬롯이며 자유 배치 엔진을 만들지 않는다.
4. B04: 제공 256×256 투명 PNG의 몸·표정·의상을 같은 좌표로 겹친 AvatarView를 만든다. idle/happy/eat 공통 표정과 3종 몸체를 쓰고 무거운 3D·골격 애니메이션을 도입하지 않는다. A가 C에 renderer 슬롯을 전달한다.
5. B05: 프로세스 재실행·원본 영수증 중복·저장 실패·잘못된 아이템을 검증하고 자기 기능 결함을 수정한다.

## 다른 파트와의 연결

입력은 A의 ArrivalCommand와 gate를 통과한 GameAction이다. 출력은 GameSnapshot·AvatarPreview·ArrivalReceipt다. C의 월드맵과 PM의 브리핑은 읽기 모델을 받는다. SDK나 C의 VisitController를 import하지 않는다. 데이터 파싱과 저장 내부 타입은 자율 설계하되 Catalog 의미와 ID를 맞춘다.

## 최소 검증과 완료

U01~06 U17~18을 우선한다. 다른 여정 이후 과거 ID가 다시 와도 같은 원본 영수증을 반환해야 한다. 재실행 뒤 외형·장식·소유·발견·pendingReceipt가 복원된다. 원자 저장을 성공하기 전에 UI에서 선물을 확정하지 않는다. UI 액션의 최신 gate 검사는 A가 연결하지만, 보유·아이템 종류·슬롯 검증은 B 서비스에서도 한다.

## 막힐 때

렌더러가 늦으면 공통 몸체 1개로 먼저 연결한다. 저장·중복 핵심을 여러 사람에게 분산하지 않는다. 부담이 크면 자산 정리·문구·독립 UI 스타일 작업을 옮긴다. PM을 보상 코드 디버거로 부르지 말고 실패 입력과 기대 결과를 먼저 작성한다.


작업 ID의 B는 기존 명세의 식별자다. 파트 선택·경계·충돌 예시는 docs/PART_GUIDE.md와 docs/18_final_review.md를 참고한다.
