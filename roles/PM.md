# PM 도착 브리핑 개발과 프로젝트 관리


목표는 도착 후 무엇이 달라졌는지 짧게 이해하게 하고, 팀이 작은 범위를 끝까지 완성하게 하는 것이다. 개발 비중은 1이며 관리 업무는 별도다. 모든 기술 결정을 대신하지 않는다.

## 읽을 것

AGENTS, docs/02·03·05·09·13·15·16, tasks/backlog, contracts/ui_contracts.md, 공식 제출 확인표. 전체 명세는 필요할 때 찾아본다.

## 직접 개발할 순서와 산출물

1. P01: fixtures/ui_samples.json의 결과로 BriefingScreen과 순수 문구 포맷 함수를 만든다. 화면은 확정된 영수증을 표시하며 보상을 계산하거나 저장하지 않는다. Compose Preview·fake부터 시작한다.
2. P02: 지역명·음식·의상·장식 이름과 참조 ID를 content에 정리하고 검증기를 유지한다. 공식 특산품 인증·매장 제휴로 설명하지 않는다. IDs를 임의로 바꾸지 않는다.
3. P03: 거리·시간 null, 추가 보상 없음, DAILY 성장, REGION 발견, DEMO 배지, 제한 상태의 미표시를 확인한다. A가 연결한 실제 결과를 표시하고 Mac에서 X02를 수행한다.

## 브리핑의 최소 모양

캐릭터와 짧은 인사, 실제로 값이 있는 이동 정보, 성장 또는 지역 선물 카드, 닫기·아이템 보기다. null을 0으로 바꾸지 않는다. 보상 없는 재방문은 없는 선물을 만들지 않는다. source가 DEMO이면 명확히 표시한다. 잘못된 ID가 오면 앱을 종료시키지 말고 일반 문구와 누락 표시를 사용하며 원인을 보고한다.

## 관리할 것

범위·날짜·가용 시간·D3/D7 부담 조정, 인수 기준, 제출용 설명·영상·README·private 접근과 동의서다. 작업 상태는 각자 docs/status를 작성한다. 매 PR을 PM 승인 대상으로 만들지 않는다. 내부 기술 질문은 먼저 해당 생산자·소비자가 해결한다.

## 검토 요청이 필요한 경우

유료 도구·서버 추가, 제품 핵심 삭제, 실제 제한 완화, 저장 호환성 파괴, 1일 이상 일정 지연처럼 큰 그림이 바뀔 때만 판단한다. 다른 표현·동일 계약의 더 쉬운 구현·일반 버그 수정은 담당자가 결정한다.

## 완료 기준

U12~13과 P01~03 코드, Mac 빌드 기록, 다른 팀원 1명과 핵심 인수 시나리오, 공식 양식·서명·CC·소스·APK 접근을 확인한다. 데이터 검증 PASS와 실제 앱 시험 PASS를 섞지 않는다. 제품 표시명은 MEMORIDE다. 내부 package·저장 키·콘텐츠 ID는 이름 변경으로 일괄 치환하지 않는다.


작업 ID의 P는 기존 명세의 식별자다. 파트 선택·경계·충돌 예시는 docs/PART_GUIDE.md와 docs/18_final_review.md를 참고한다.

1.2 추가 확인: I06의 비동기 닫기 실패·재시도. 새로운 관리 절차가 아니라 해당 기능의 기존 시험에 함께 포함한다.

## 시작 안내와 자율 설계

[환경 설치](../docs/ONBOARDING.md)와 [AI 설정](../docs/LOCAL_AI_SETUP.md)을 마친 뒤 [이 역할의 첫 작업·시작 프롬프트](../docs/FIRST_TASKS.md#pm)로 진행한다. 세부 작업 분해·내부 코드·UI 설계는 담당자가 자기 AI와 자율적으로 결정한다. 기존 계약 안의 내부 계획과 일반 결함마다 PM 승인을 요청하지 않는다. A01 공통 앱을 받은 뒤 같은 빌드 파일을 사용하며 별도 Android 앱을 만들지 않는다.
