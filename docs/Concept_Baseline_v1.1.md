# 카일랜드 최종 컨셉과 MVP 개발 기준

버전 1.1   |   기준일 2026년 10월 30일   |   적용 범위 2주 프로토타입

이 문서는 카일랜드의 정체성과 이번 개발 범위를 고정하는 팀 공통 기준이다. 핵심 경험은 유지하고, 구현 방식은 실제 Pleos 지원과 검증 결과에 따라 조정한다. 향후 확장 항목은 이번 MVP의 완료 조건에 포함하지 않는다.

## 1 프로젝트 정의와 개발 목적

카일랜드는 자동차로 함께한 일상과 여행이 나만의 캐릭터와 섬에 반영되는 차량 연동형 라이프 시뮬레이션 게임이다. 주행 중에는 직접 게임을 조작하지 않는 캐릭터 동행 경험을 지향하고, 이동 전후에는 짧게 섬을 확인하며 음식을 먹이고 옷과 장식을 바꾼다.

초기 대상은 어린 자녀와 자동차로 이동하는 가족이다. 운전자나 동승자가 차 안에 오래 머물러 게임을 한다고 전제하지 않는다. 출발 전 준비 시간과 도착 후 잠깐의 여유에도 하나의 행동이나 변화를 확인할 수 있게 한다.

개발 배경은 반복되는 생활 이동의 단조로움, 가족이 함께 즐길 작은 경험의 필요성, 지역 방문을 캐릭터의 생활과 연결할 기회다. 이동 기록을 상세한 추억 앨범으로 축적하는 기능은 장기 비전으로 남긴다.

## 2 범위에 관한 확정 결정

| 구분 | 이번 개발 기준 |
| --- | --- |
| 유지 | 캐릭터와 섬, 주행 동행 모의 화면, Daily Island, Journey Archipelago, 지역 음식·의상·장식, 짧은 여정 브리핑, 가상 캐릭터 방문 |
| 제외 | Car Care와 차량 점검·정비 게임. 별도 차량 건강 평가와 운전 점수도 구현하지 않는다. |
| 향후 계획 | 추억의 연대기·사진 앨범·장기 방문 이력·고도화된 개인화. 사고 상황에서 연락 선택지를 안내하는 지원도 후속 검토한다. |
| 조건부 연동 | Car Sync를 독립 상품 기능이나 화면으로 만들지 않는다. 핵심 경험에 필요한 목적지·도착·차량 정보 연결만 수행한다. |
| 기본 저장 | 캐릭터 선택, 아이템 소유, 섬 배치, 지역 발견 여부와 중복 처리 상태는 저장한다. 이는 추억·기록 서비스와 구분한다. |

## 3 핵심 사용자 경험

### 3 1 섬에서 보내는 짧은 시간

캐릭터는 섬의 중심에 머물며 사용자의 선택에 반응한다. 냉장고에서 지역 음식을 골라 먹이기, 옷장에서 의상 바꾸기, 장식 배치와 표정 관찰을 제공한다. 장시간 접속, 실시간 생존 관리, 방치 페널티는 요구하지 않는다.

### 3 2 주행 중 동행

섬에서 꾸민 캐릭터의 외형을 주행 동행 화면에서도 유지한다. 지도·경로·속도·회전 안내·경고 등 중요 정보를 가리지 않는 작은 고정 영역과 낮은 빈도의 표정·자세 변화를 지향한다. 숨기기 기능을 제공하며, 주행 중 꾸미기나 보상 수령을 요구하지 않는다.

직접 조작하지 않는다는 이유만으로 안전성이 입증되는 것은 아니다. 실제 주행에서의 표시와 애니메이션은 플랫폼 정책과 사용성 검증을 따른다. 이번 MVP의 동행 화면은 주차 상태에서 실행하는 자체 제작 모의 내비 화면으로 체험시킨다. [3]

### 3 3 이동을 마친 후

캐릭터가 이번 이동의 확인 가능한 정보, 섬의 변화, 획득한 기념품을 한 장의 짧은 브리핑으로 전달한다. 브리핑은 바로 닫을 수 있게 하고, 일반 운행 수치를 길게 나열하거나 점수화하지 않는다. 평균속도와 급정거 횟수는 MVP 필수 지표에서 제외한다. 실제 측정과 정의를 검증한 지표만 선택적으로 표시한다.

사용자는 이후 음식·의상·장식 중 원하는 것만 확인하고 앱 이용을 마칠 수 있다. 기본 이용 흐름은 섬 준비, 동행 체험, 도착, 브리핑, 섬 변화와 기념품 사용으로 이어진다.

## 4 이동이 섬으로 바뀌는 성장 규칙

| 체계 | 역할 | MVP 표현 |
| --- | --- | --- |
| Daily Island | 익숙한 생활 이동의 축적 | 일상 여정 완료에 따라 정원이나 생활시설의 준비된 다음 단계가 열린다. |
| Journey Archipelago | 새로운 지역의 발견 | 등록된 지역 첫 도착에 따라 월드맵의 구역과 지역 기념품이 열린다. |

Daily Island는 기존 공간의 발전, Journey Archipelago는 새로운 공간의 발견으로 시각적 결과를 구분한다. 실제 지형 자동 생성이나 정교한 경로 군집화 대신 준비된 시설 단계와 군도 카드를 사용한다.

일상 여부는 초기에는 시연 시나리오 태그로 지정할 수 있다. 일반 사용자에게 매번 출퇴근·여행 선택을 강제하지 않으며, 해당 선택만으로 실제 방문을 인증하지 않는다.

- 주행거리와 속도에 보상을 단순 비례시키지 않는다. 일상 성장 보상은 하루 단위 상한을 두고 시연에 필요한 변화만 구현한다.

- 지역 발견과 최초 기념품 지급은 프로필과 지역 조합으로 한 번만 처리한다. 같은 도착 이벤트의 반복 수신으로 중복 지급하지 않는다.

- 목적지 선택은 방문 완료가 아니다. 보상에는 실제로 확인한 도착 이벤트 또는 명시적인 가상 도착 입력을 사용한다.

## 5 지역 콘텐츠와 캐릭터 상호작용

| 콘텐츠 | 사용 방식 | 설계 기준 |
| --- | --- | --- |
| 음식 | 냉장고에서 선택하고 먹기 반응 관찰 | MVP에서는 소모·구매 경제 없이 식사 연출을 우선한다. |
| 의상과 소지품 | 입기·쓰기·들기 | 섬과 주행 동행 모의 화면에서 동일한 선택을 유지한다. |
| 환경과 시설 | 섬의 배경·슬롯에 배치 | 소유한 장식만 사용하고, 배치 결과를 저장한다. |

빵모자, 지역 음식, 은행나무 장식 등은 지역의 특징을 자체 디자인으로 표현하는 콘텐츠 예시다. 실제 제휴나 브랜드 사용 허가를 확보한 것으로 설명하지 않는다. 지역 도착과 특정 상점 방문은 별도 조건으로 구분한다.

월드맵과 간단한 도감은 지역 발견 여부와 보유 기념품을 보여주는 수집 UI로 사용한다. 상세 방문 날짜 목록, 여정 타임라인, 사진 앨범과 개인 서사 생성은 이번에 개발하지 않는다.

## 6 캐릭터 방문과 동의 기반 소통

캐릭터는 사용자의 의사를 정해진 표현으로 전달하는 메신저 역할을 한다. 이번 구현 대상은 앱 내부의 가상 차량 A와 B이며, 실제 차량 식별과 차량 간 무선 통신은 수행하지 않는다.

사용자가 가상 대상과 메시지 의도를 선택하거나, 음성 요청을 가정한 시나리오를 시작한다.

상대 화면에 발신 목적을 포함한 방문 요청이 표시된다. 단순한 친목 방문처럼 목적을 숨기지 않는다.

수락하면 캐릭터가 방문해 고정 문구를 전달한다. 거절·무응답·만료이면 방문하지 않는다.

대화 종료 후 캐릭터가 돌아간다. 반복 요청을 제한하며 소통 횟수에 게임 보상을 주지 않는다.

요청 예시: 뒤 차량의 캐릭터가 주행 관련 메시지를 전하고 싶어 해요. 받아보시겠어요?

전달 예시: 혹시 추월 중이 아니라면, 안전할 때 주행차로를 확인해 주실 수 있을까요?

수락은 메시지 열람 동의이며 차선 변경 약속이 아니다. 상대의 잘못을 앱이 판정하거나 즉시 행동을 강요하지 않는다. 이 구조는 공격적 표현을 제한하는 소통 방식을 제안하며, 갈등·보복운전 감소 효과를 입증한 것으로 주장하지 않는다.

임의의 캐릭터 이름을 통한 상시 음성 호출과 자유 발화 해석도 MVP 완료 조건에 포함하지 않는다. 해당 장면은 시나리오로 재현할 수 있다. 실제 주행 중 사용 허용은 별도 검증 대상으로 둔다.

## 7 프로토타입 화면 구성

| 화면 | 필수 경험 | 구현 원칙 |
| --- | --- | --- |
| 메인 섬 | 캐릭터 관찰과 시설 변화 | 이용의 중심 공간 |
| 꾸미기 | 의상 변경과 장식 배치 | 인벤토리 소유 정보를 공통 사용 |
| 여행과 내비 연동 | 지역 선택·목적지·여정 상태 | 기술 상태는 별도 시연 패널로 분리 |
| 주행 동행 모의 화면 | 꾸민 캐릭터의 절제된 동행 | 기본 내비 개조로 오인하지 않게 표시 |
| 도착과 브리핑 | 이번 이동·성장·기념품 | 짧게 확인하고 닫을 수 있음 |
| 월드맵과 지역 상세 | 군도 발견과 지역 콘텐츠 | 고정 구역을 열어가는 표현 |
| 인벤토리와 간단 도감 | 음식·의상·장식 사용과 발견 목록 | 장기 여정 기록 기능은 제외 |
| 가상 차량 방문 | 요청·수락·거절·메시지 | 가상 상대임을 명시 |

이 표는 필요한 화면 상태를 정의한다. 각 항목을 모두 독립 메인 메뉴로 만들 필요는 없다. 섬의 냉장고·옷장·장식함, 월드맵의 지역 상세, 도착 카드의 결과 확인으로 자연스럽게 연결한다.

## 8 Pleos 활용과 구현 경계

NaviHelper는 차량 내비게이션의 목적지·경유지·경로 요청과 정보 조회, 상태 이벤트를 제공하는 연동 도구다. 이번 개발에서는 목적지 요청과 조회를 우선 검증하고, 도착 이벤트를 게임의 입력으로 연결한다. 실제 전달 이벤트는 내비 구현과 상태에 따라 달라질 수 있다. [2]

| 영역 | 우선 적용 | 실패하거나 지원되지 않을 때 |
| --- | --- | --- |
| 내비 연동 | 목적지 요청과 조회, 변경 반영 | 실패 상태를 표시하고 가상 입력으로 체험을 이어감 |
| 도착 | 유효한 목적지 도착 이벤트 | 가상 도착임을 표시한 시연 입력 사용 |
| 차량 정보 | 브리핑에 필요한 최소 거리·시간 정보 | 해당 수치는 생략하거나 가상 값으로 명확히 표시 |
| 주행 화면 | 자체 제작 모의 내비와 캐릭터 | 기본 내비 오버레이나 계기판 변경을 약속하지 않음 |

Car Sync는 위 연동을 수행하는 내부 역할로만 취급한다. 별도 센서 대시보드·차량 상태 콘텐츠를 추가하지 않는다. 차량 정보 수집이 핵심 흐름을 돕지 않거나 일정에 부담을 주면 해당 수집을 제외하고, 내비 연동에 집중한다.

SDK 연동 코드와 가상 입력은 동일한 게임 이벤트 형식을 사용하되 출처를 구분한다. 가상 입력으로 성공한 장면을 실제 SDK 검증 결과로 설명하지 않는다. 기본 내비 화면에 캐릭터를 직접 삽입하는 방식은 플랫폼 통합 검증 대상으로 남긴다.

앱 생명주기·백그라운드 이벤트·권한을 확인한다. 미수집 수치를 0으로 간주하거나 누락 구간을 임의로 채우지 않는다. 플랫폼 제한 상태에서는 게임 조작과 방문 연출을 중단한다. 주차와 일시 정지를 같은 상태로 처리하지 않는다. [3]

## 9 2주 MVP 제작 범위와 완료 기준

제작량의 계획 기준은 캐릭터 외형 3종, 시범 지역 3곳, 지역별 음식·의상·장식 각 1개, 메인 섬 1개와 단순 시설 성장, 지역 발견 카드, 가상 차량 A와 B다. 캐릭터는 공통 동작 구조를 사용하고, 시설과 군도는 준비된 단계·배치를 전환한다. 세부 수량과 미술 자산은 초기 실행 확인 후 PM이 범위 안에서 조정할 수 있다.

완성 목표는 출시 수준의 게임이 아니라, 한 여정이 동행·도착·성장·기념품 사용·방문으로 이어지고 반복 시연 가능한 프로토타입이다. 실제 차량, 유료 서버, 실행 중 LLM API, 실물 구매를 개발 전제로 두지 않는다.

| 검증 대상 | 완료 기준 |
| --- | --- |
| 기본 경험 | 선택한 캐릭터가 섬과 동행 모의 화면에서 같은 의상을 유지한다. |
| 성장 | 일상 여정과 새 지역 도착이 서로 다른 시각적 결과를 만든다. |
| 기념품 | 음식 반응·의상 착용·장식 배치가 각각 최소 한 번 동작한다. |
| 방문 | 수락 시에만 등장하고 거절·만료 후에는 등장하지 않는다. |
| 저장과 중복 | 재실행 시 소유·배치가 복원되고 같은 도착으로 보상이 중복되지 않는다. |
| Pleos 검증 | 실제 API 호출·응답·오류와 가상 입력의 범위가 문서·영상에서 일치한다. |
| 재현 | 초기화 후 전체 흐름을 반복할 수 있고 README와 release APK가 제공된다. |

첫 이틀에는 Pleos 실행과 최소 내비 요청·조회에 집중한다. 이 부분이 실패하면 원인을 기록하고 범위를 조정한다. 전부 가상 입력인 결과물과 실제 연동 프로토타입은 동일한 기술 검증 수준으로 취급하지 않는다.

## 10 개발 운영 기준

개발 노력의 목표는 A:B:C:PM = 2:2:2:1이다. 코드 줄 수나 화면 수가 아니라 구현·시험·오류 수정에 필요한 상대 노력으로 본다. PM의 관리 업무는 이 비율 밖이다. D3과 D7에 실제 부담을 확인하고 독립 작업을 조정한다.

화면만 나누지 않고 기능의 데이터·규칙·화면·검증을 묶어 소유한다. 공통 데이터 형식과 AppRoot 연결은 A가 관리하며 다른 세 명은 샘플 입력으로 시작한다. 하나의 Android 앱 안에서 담당 디렉터리를 나누고 기능 간 직접 참조를 줄인다.

PM은 도착 브리핑과 콘텐츠 검증을 직접 개발한다. 브리핑은 저장된 결과를 표시하며 보상·SDK·게임 저장을 직접 실행하지 않는다. 각 개발자가 자기 내부 설계와 결함을 해결하고 PM은 핵심 범위·비용·제한·큰 일정 변경만 판단한다.

Codex와 Claude에는 짧은 AGENTS.md, 담당 역할 카드, 필요한 공통 계약과 완료 기준만 제공한다. 같은 파일을 여러 작업이 동시에 수정하지 않는다. 각 기능 작성자가 구현·검증·오류 수정을 맡고, 작은 PR로 D3부터 통합한다. 개발 중에는 MD 문서를 원본으로 관리한다.

일정이 부족하면 자산 수·추가 애니메이션·상세 통계·경유지 등을 줄인다. 캐릭터와 섬, 일상 성장과 지역 발견의 차이, 기념품 사용, 가상 방문의 수락·거절이라는 핵심은 유지한다.

## 11 개발 배경과 기대효과 및 향후 계획

### 11 1 개발 배경과 기대효과

손글씨 피드백의 출퇴근 이동에서도 즐거움을 찾자는 관점은 Daily Island의 개발 배경으로 반영한다. 동승자 모두가 즐길 수 있어야 한다는 의견은 가족이 짧게 음식·의상·장식을 함께 고르는 사용 장면과 기대효과에 반영한다. 별도 다인 접속 기능을 의미하지 않는다.

기대효과는 이동 경험의 개인화, 가족의 작은 공동 경험, 지역 콘텐츠에 대한 관심, 정중한 간접 소통 방식의 탐색이다. 장시간 이용이나 추가 운전을 유도하지 않는 방향을 유지한다. 고객 유지율·지역 소비 증가·갈등 감소는 후속 검증 대상이며 이미 달성한 성과로 쓰지 않는다.

### 11 2 향후 검토 항목

- 추억과 기록: 여행 연대기·사진·기념일·장기 개인화. 현재 MVP의 수집 상태 저장과 구분한다.

- 긴급 상황 지원: 사고 등 상황에서 필요한 연락 선택지를 캐릭터가 안내하고 사용자의 확인 후 연락으로 연결하는 방식. 사고 자동 판정·자동 신고·보험사 연동은 별도 권한·안정성·협력 조건을 검증한다.

- 표현과 플랫폼 확장: 기본 내비 화면의 정식 캐릭터 통합, 계기판 개인화, 음성 호출, 실제 차량 간 전달. 각 기능은 플랫폼 지원과 주행 정책을 별도로 검증한다.

- 가족과 지역 확장: 추가 캐릭터·지역 콘텐츠·공동 이용과 제휴. 이번에는 계정 동기화·실시간 멀티플레이·결제를 구현하지 않는다.

Car Care는 이번 제품 범위에서 제외한다. 향후 목록에 있다는 이유만으로 현재 완료 조건에 추가하지 않는다. 새 기능은 PM이 사용자 가치·기간·검증 부담을 확인한 뒤 버전 변경으로 반영한다.

## 12 사실성과 문서 유지 원칙

본 문서의 컨셉·포함 및 제외 범위는 개발의 기준이다. 배포 화면·APK·영상·기획서는 같은 버전의 기능 범위를 설명해야 한다. SDK 지원이 확인된 사실, 실제 수행한 시험, 시뮬레이션, 향후 가설을 구분해 기록한다.

캐릭터 동행의 주의 분산 최소화와 동의 기반 메시지의 갈등 완화는 설계 목표다. 안전성·사고 예방 효과를 입증한 것으로 주장하지 않는다. 개별 기능과 전체 조합의 세계 최초 또는 수상 가능성을 수치로 단정하지 않는다.

공식 평가는 차량특화성·창의성·기술 활용성·사업성이며 세부 배점은 공개되지 않는다. 목적지와 여정 정보가 게임 경험에 연결되는 장면을 제시하고, 필요한 기능을 적절히 쓴 근거로 설명한다. [1]

## 13 버전 1 1에서 보완한 개발 합의

제품 컨셉과 Car Care 제외·기록 서비스 향후 계획은 유지했다. PM의 실제 개발을 추가하고 C의 월드맵 표시를 명확히 해 작업량을 분산했다.

공통 계약, 샘플 입력, 단일 게임 저장자, 실제 제한과 모의 여정의 분리, 조기 통합, 단계별 시험을 specification과 MD 개발 문서에 정리했다. 세부 클래스·함수·화면 내부 설계는 각 담당자가 자율적으로 정한다.

PM이 private 저장소를 만들고 파트 브랜치에서 작은 PR로 main에 합친다. D11 기능 동결 후 최종 검증된 main에 태그를 붙인다. 로컬 검증을 기본으로 하고 Actions는 수동 실행만 제공한다. Free private에서 강제 브랜치 보호가 지원된다고 가정하지 않는다.

이 문서와 specification은 개발 전 기준이다. 현재 Android 앱·APK·실제 SDK 성공을 확인한 결과물이 아니다. 정적 콘텐츠 검증과 실제 시스템 시험을 구분한다. 오류를 줄이기 위한 설계이며 무결함·주행 안전·일정·수상을 보장하지 않는다.
