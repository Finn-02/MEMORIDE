# MEMORIDE 파트 선택과 개발 경계

이 문서는 팀원 세 명이 파트 1·2·3을 선택하고, 서로 무엇을 주고받는지 이해하기 위한 안내다. PM은 주준경이며 도착 브리핑도 직접 개발한다. 세부 클래스·화면 내부 설계는 담당자가 Codex·Claude와 자율적으로 진행한다.

## 1 파트를 선택하는 방법

| 역할 | 만드는 경험 | 먼저 관심을 둘 것 | 계획 점수 |
|---|---|---|---|
| 파트 1 A | 차량 입력에서 앱 전체 흐름까지 | Android 설정·비동기 상태·SDK·빌드 | 20 |
| 파트 2 B | 섬·캐릭터·기념품의 변화 | 게임 규칙·상태 저장·꾸미기 UI | 20 |
| 파트 3 C | 동행과 가상 방문을 체험하는 화면 | 상호작용 UI·타이머·시연 흐름 | 20 |
| PM P | 도착 후 달라진 것을 알려주는 화면 | Compose 기초·문구·데이터 검증 | 10 |

점수는 실제 소요 시간을 보장하지 않는 상대 추정치다. 파트 1은 SDK 불확실성, 파트 2는 구현량, 파트 3은 여러 화면과 동의·타이머 검증의 부담이 있다. 특정 파트를 쉬운 파트로 지정하지 않는다. D3과 D7에 진행 결과를 보고 자산 정리·독립 UI 등 1~3포인트 작업을 옮긴다. 저장·보상 핵심은 여러 명으로 쪼개지 않는다.

각자 선호를 한 번 공유하고 중복 선택만 조정한다. 파트 1은 기준 Windows PC에서 Android/Pleos 환경을 일찍 확인할 수 있는 사람이 맡는 편이 좋다. 배정 후 PM이 config/team.json에 GitHub ID를 기록한다. 작업 ID A/B/C는 기존 명세와 연결하기 위한 별칭이다.

## 2 파트 1 플랫폼과 차량 여정

파트 1은 공통 앱과 기능 연결을 만든다. Android 프로젝트·Gradle wrapper·테마·라우터를 먼저 공유하고, 차량 또는 DEMO 입력을 JourneySnapshot과 ArrivalCommand로 바꾼다. 실제 이용 제한과 미확인 상태를 관리하며 release APK도 만든다.

개발 순서는 A01 공통 앱·계약 → A02 fake 여정 → A03 실제 Pleos 관찰 → A04 도착·저장·브리핑 연결 → A05 첫 서명 release → A06 통합 검증이다. 공통 앱은 먼저 공유하며 SDK 성공을 기다렸다가 내보내지 않는다.

입력은 목적지 선택·SDK 콜백·파트 3의 DEMO 명령이다. 출력은 여정 상태·gate·검증된 도착 명령이다. 파트 2에 보상 계산을 넘기고, 저장된 영수증을 PM 화면에 전달한다. 브리핑 레이아웃·방문 문구·게임 버그는 해당 작성자가 수정한다.

주요 소유 경로는 app의 빌드 파일·Manifest·Application·MainActivity, app 패키지, core/contract·core/platform·최소 core/ui다. 다른 담당자는 자기 feature에서 작업한다. AppRoot는 작은 조립부로 유지한다.

첫 완료물은 같은 버전으로 빌드되는 공통 앱과 임시 화면이다. 이후 목적지 변경의 오래된 콜백 거부, 저장 실패 재시도, reset 후 늦은 입력 차단, 실제 gate 우선을 시험한다. D8까지 서명 APK를 파트 3의 백업 PC에 설치한다. SDK가 막히면 D1~2 시도 결과를 기록하고 DEMO와 성공 범위를 구분한다.

상세 작업 카드는 roles/A.md와 tasks/backlog.md의 A01~06이다.

## 3 파트 2 섬과 캐릭터 게임

파트 2는 이동 완료가 무엇을 바꾸는지 결정하고 저장한다. 섬·캐릭터 선택·의상·음식·장식·인벤토리를 만들며, 게임 진행 상태를 쓰는 유일한 담당자다. DataStore 한 인스턴스와 한 저장 경로를 사용한다.

개발 순서는 B01 기본 상태·서비스 → B02 한 지역 보상·원자 저장 → B03 섬·아이템 사용 → B04 캐릭터 레이어 렌더러 → B05 복원·중복·실패 검증이다. 처음부터 세 지역·모든 그림을 완성하지 않고 한 캐릭터와 한 지역으로 연결한다.

입력은 ArrivalCommand와 gate를 통과한 GameAction이다. 출력은 GameSnapshot·AvatarPreview·ArrivalReceipt다. SDK 객체를 직접 읽지 않고, 파트 3의 방문 상태도 저장하지 않는다. PM 브리핑 문구에서 선물 개수를 다시 계산하게 만들지 않는다.

주요 소유 경로는 feature/island, game 저장 코드, char_·item_ 자산과 렌더러다. 몸체·표정·의상을 같은 256×256 좌표에 겹치는 2D 방식으로 시작한다. 제공 자산은 초안이며 3D나 복잡한 애니메이션 엔진을 도입하지 않는다.

첫 완료물은 같은 도착을 두 번 받아도 한 번만 지급하고 재실행해도 결과가 남는 저장 기능이다. 의상 소유·아이템 종류·장식 3슬롯 검증, 저장 실패에서 상태 보존, 과거 영수증 재조회도 확인한다. 부하가 크면 자산 변형을 옮기되 보상·저장 핵심은 유지한다.

상세 작업 카드는 roles/B.md와 tasks/backlog.md의 B01~05다.

## 4 파트 3 동행과 방문 및 시연

파트 3은 심사자가 컨셉을 직접 체험하는 화면을 만든다. 자체 도형 지도의 동행 모의 화면, 가상 발신·수신 캐릭터 방문, 월드맵·간단 도감, 수동 시연 패널을 맡는다. 실제 차량 두 대·번호판 식별·통신 서버를 만들지 않는다.

개발 순서는 C01 임시 캐릭터 동행 → C02 방문 상태와 동의 → C03 월드맵 읽기 UI → C04 수동 시연·반복·초기화 요청 → C05 타이머·화면 이탈·백업 설치 검증이다. 캐릭터는 파트 2가 완성할 때까지 같은 크기의 회색 임시 슬롯을 사용한다.

입력은 여정·gate·게임 읽기 상태·캐릭터 슬롯이다. 출력은 목적지·여정·초기화 요청과 로컬 방문 반응이다. 아이템 지급이나 게임 저장 파일에 직접 접근하지 않는다. 시연 완료 요청은 A의 처리 결과를 await하고 저장 성공도 확인한다.

주요 소유 경로는 feature/companion·visit·world·demo다. 방문 요청은 목적을 먼저 보이고 수락·거절을 동등하게 제공한다. 거절·만료·철회·과거 요청의 늦은 수락에서 캐릭터가 나타나면 안 된다. 같은 프로세스 안의 가상 A/B는 개발 파트 A/B와 다른 의미이므로 화면에는 가상 앞차·내 차처럼 표시한다.

첫 완료물은 수락할 때만 방문하는 가상 상황이다. 화면 이탈·background·실제 제한에서 연출과 타이머를 종료한다. SDK·게임 renderer가 없어도 샘플로 진행한다. 일정이 밀리면 자동 재생·확대 지도·화려한 걸음을 먼저 줄인다. Windows PC를 release 설치·시연 백업으로 준비한다.

상세 작업 카드는 roles/C.md와 tasks/backlog.md의 C01~05다.

## 5 PM 브리핑 개발과 진행 관리

PM은 브리핑 화면과 순수 문구 선택 함수를 직접 만든다. 저장된 ArrivalReceipt·Catalog·AvatarPreview를 받아 인사·확인된 이동 정보·섬 변화·기념품을 표시한다. SDK 호출·보상 계산·게임 저장은 하지 않는다.

개발 순서는 P01 샘플 브리핑 → P02 지역 콘텐츠·fixtures·검증기 → P03 실제 결과 연결·예외·Mac 빌드다. null을 0으로 바꾸지 않고, 재방문에서 없는 새 선물을 만들지 않으며, DEMO 출처를 표시한다. 닫기·아이템 열기는 A가 제공한 비동기 콜백을 호출한다.

주요 소유 경로는 feature/briefing, content, fixtures 내용과 검증기다. Catalog 참조 ID를 마음대로 바꾸지 않는다. B가 만든 그림의 좌표·레이어는 B가 관리한다. PM은 문구와 기념품 주제를 제안할 수 있다.

관리는 범위·일정·가용 시간·D3/D7 부담 조정·인수·영상·기획서·접수다. 관리 시간은 개발 10포인트 밖이다. PM이 모든 PR을 승인하거나 전원 오류를 대신 해결하지 않는다. 보상·동시성은 작성자와 영향 파트가 검토한다.

유료 기능·핵심 범위 삭제·실제 제한 완화·저장 호환성 파괴·1일 이상 지연만 PM 판단으로 올린다. 내부 구현·스타일·일반 결함은 담당자가 자율 처리한다. 상세 카드는 roles/PM.md와 P01~03이다.

## 6 연결과 시험 및 첫 공동 실행

대전 DEMO의 예: 파트 1이 도착 명령을 만든다 → 파트 2가 발견·선물·영수증을 한 번에 저장한다 → PM 브리핑이 결과를 보여준다. 파트 3의 월드맵은 같은 저장 상태를 읽고, 동행 화면은 같은 외형을 캐릭터 슬롯으로 받는다. 파트 3의 방문은 이 저장 흐름과 독립이다.

공통 타입과 AppRoot는 파트 1이 관리한다. 다른 feature의 내부 ViewModel·저장소·SDK를 직접 import하지 않는다. 연결 요청에는 함수 호출 예제·입력·기대 결과만 적는다. 계약 변경이 필요할 때만 templates/communication.md를 사용한다. 대기 중에는 현재 계약과 fake로 계속한다.

각 작성자는 자기 단위 시험을 수행한다. 연결은 생산자·소비자가 함께 확인하고, 시스템 빌드·설치는 파트 1과 백업 파트 3이 확인한다. PM은 다른 팀원 한 명과 핵심 사용자 흐름을 인수한다. 기본 리뷰 짝은 파트 1↔PM, 파트 2↔파트 3이며 위험한 저장·도착 연결만 해당 담당자가 추가 확인한다.

D1 공통 앱과 계약, D3 한 지역 전체 흐름 main, D8 첫 release 설치, D11 동결, D13 내부 제출을 목표로 한다. 날짜는 docs/16_kickoff_process.md의 11월 2일 시작 가정이다. 설치·SDK 불확실성 때문에 2주 성공을 보장하는 일정은 아니다.

시작 직전 확인은 배정 완료, 로컬 정적 검사, A01 첫 빌드, 각자의 첫 입력·완료 조건 확인이면 충분하다. 모든 화면·내부 클래스를 PM이 설계할 때까지 기다리지 않는다.
