# 18 명칭 확정과 최종 개발 경계

## 18 1 이름과 버전의 구분

MEMORIDE는 제품 표시명과 저장소 이름이다. 카일랜드는 기존 섬 세계관으로 유지한다. 1.2는 문서·브랜딩 버전이며 contentVersion 1.1.0·저장 schemaVersion 1·io.kailand와 콘텐츠 ID는 그대로다. 이 자료에 실제 앱 코드가 생겼다는 의미는 아니다. 컨셉 1.1 원본은 references/frozen에 보존했고 컨셉 1.2는 이름·설명·파트 표기만 보완한다.

파트 1=A, 파트 2=B, 파트 3=C, PM=P다. A/B/C는 명세·작업·시험에서 사용하는 역할 식별자다. 가상 차량 A/B와 혼동하지 않도록 사용자 화면에는 내 차·가상 앞차를 사용한다. 인원 배정은 config/team.json 한 곳에서 관리한다.

## 18 2 화면 이동을 명시적으로 연결하기

섬의 여정 시작 버튼은 onPrepareJourney로 S03을 연다. onOpenWorld는 S06, onOpenDemo는 진행자 S08로 이동한다. 월드맵의 onSelectRegion은 A가 S03의 목적지 후보를 채우는 동작이며, 지역 선택만으로 내비 시작·도착·보상을 실행하지 않는다. 최종 목적지 요청은 S03의 사용자 확인 후 실행한다.

C는 월드맵을 읽고 B는 소유 상태를 계산한다. 음식·의상·장식은 B의 GameAction을 통해서만 적용한다. C의 수집 목록은 읽기 전용이며 사용 버튼은 A를 거쳐 B의 인벤토리를 연다. 공유 내비게이션 명령을 여기저기서 재정의하지 않는다.

## 18 3 브리핑 닫기의 비동기 결과

PM의 onDismiss와 onOpenItems는 suspend () -> MutationResult 콜백이다. PM은 클릭 처리 코루틴에서 한 번 호출하고 처리 중 버튼 중복 입력을 막는다. A가 현재 gate·foreground와 표시 중 journeyId를 확인하고 B의 acknowledgeReceipt를 await한다. Success 뒤에만 화면을 이동한다. 저장 실패이면 브리핑을 유지하며 재시도를 제공하고 보상을 다시 계산하지 않는다.

B는 요청 ID가 현재 pendingReceiptId와 같을 때만 이를 지운다. 이미 처리되어 pending이 null이고 원본 영수증이 있으면 부작용 없이 Success로 응답할 수 있다. 다른 최신 pending이 있으면 Rejected로 반환하고 새 영수증을 보존한다. A는 오래된 닫기 요청이 새 브리핑을 닫지 않게 현재 결과를 다시 표시한다. 물리적 뒤로 가기도 같은 처리 경로를 쓴다.

## 18 4 초기화의 잠금 순서

A는 게임 명령·도착 저장과 reset을 조정하지만, Mutex를 잡은 채 Runner나 방문 job의 cancelAndJoin을 기다리지 않는다. Runner가 같은 Mutex를 기다리고 있으면 서로 기다리는 문제가 생길 수 있기 때문이다.

권장 순서는 세 단계다. 먼저 조정 Mutex 안에서 기존 쓰기가 끝난 뒤 새 입력 차단과 generation 증가를 기록하고 잠금을 푼다. 다음으로 Runner·여정 listener·방문을 취소하고 종료를 기다린다. 마지막으로 Mutex 안에서 B의 게임 초기화를 실행하고 초기화가 성공했을 때만 새 입력을 연다. 실패하면 오류와 재시도를 유지한다. 이전 세대의 콜백·명령은 잠금을 얻은 뒤 generation을 다시 검사하고 거부한다. 호출자는 reset을 수행 중인 자기 job을 join하지 않는다.

이 구조는 별도 서버나 메시지 브로커 없이 직렬화를 유지하기 위한 시작안이다. 담당자는 더 단순한 구현이 동일 조건을 만족하면 채택할 수 있다. 핵심은 늦은 쓰기와 교착을 작은 시험으로 확인하는 것이다.

## 18 5 자주 충돌하는 경계의 판단

| 상황 | 결정 담당과 처리 | 바꾸지 않을 것 |
|---|---|---|
| 캐릭터 그림이 늦음 | B가 renderer, C는 임시 슬롯 | C가 B 내부 구현 직접 참조하지 않음 |
| 완료와 초기화가 겹침 | A가 세대·순서, B가 원자 저장 | C나 PM이 파일을 직접 지우지 않음 |
| 기념품 개수가 다름 | B의 영수증·상태가 기준 | PM 문구에서 새 보상 계산 금지 |
| 닫기 저장이 실패함 | A가 실패 전달, PM은 화면 유지 | 성공처럼 이동·추가 지급 금지 |
| 공용 테마·AppRoot 변경 | A가 작은 조립 변경 | 전원 동시 편집·대규모 공통화 금지 |
| 새 지역 문구·데이터 | PM이 Catalog 원본, B가 자산 정렬 | ID·원본 복사본 이중 수정 금지 |
| SDK 미지원·장비 실패 | A가 근거·범위 기록, PM은 제출 설명 | DEMO를 실제 SDK 성공으로 표시 금지 |

## 18 6 추가 연결 확인

기존 U/I/S/AC와 X01~03 외에 I06을 둔다. 한 번의 수동 연결 시나리오로 섬→여정 준비, 월드맵→목적지 후보, 도착→브리핑, 닫기 실패→유지, 재시도→이동을 확인한다. U19는 B의 오래된 acknowledge가 최신 pending을 지우지 않는지, U20은 A의 reset 중 Runner 대기·늦은 입력에서 교착과 재지급이 없는지 확인한다. 아직 이 Android 시험을 수행하지 않았다.

## 18 7 시작 판단과 다음 행동

작은 공통 계약과 독립 샘플을 바탕으로 준비 작업을 시작할 수 있다. 실제 개발 가능성의 남은 큰 변수는 도구 설치·팀 시간·Pleos 환경과 입력이다. D1 첫 빌드와 D2 관찰로 줄이며 D3 한 지역 수직 흐름을 먼저 연결한다. 이름이 정해진 뒤에도 정적 도구 통과를 앱 완성으로 해석하지 않는다.
