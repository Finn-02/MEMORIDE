# 9 테스트 전략과 품질 기준

## 9 1 네 가지 테스트를 가볍게 운영하기

단위 테스트는 계산과 상태 전이, 통합 테스트는 두 경계의 연결, 시스템 테스트는 설치된 APK의 전체 동작, 인수 테스트는 사용자가 기대한 경험을 확인한다. 같은 시나리오를 네 종류의 문서와 자동화로 중복 구현하지 않는다. 핵심 위험은 작은 자동 테스트로 고정하고, 화면·설치·플랫폼은 짧은 수동 재현으로 확인한다. [S12]

| 수준 | 대상과 책임 | 최소 방법 | 실행 시점 |
|---|---|---|---|
| 단위 | B의 보상·저장 규칙, C의 방문 상태, PM 문구·콘텐츠, A의 이벤트 변환 | JUnit과 가짜 입력, 콘텐츠는 Python 표준 라이브러리 | 담당 파트 변경 때 |
| 통합 | 여정 완료→게임 저장→브리핑, 외형→동행, 요청→수락 | FakeAdapter와 실제 GameService 연결 시험 | 관련 계약 변경·통합 때 |
| 시스템 | 실제 Pleos 또는 명시된 Android 시험 환경의 APK | 설치·복원·제한·창 크기·오류 수동 목록 | D7, D10, release 후보 |
| 인수 | 가족의 짧은 이용과 심사 시연 | PM과 다른 팀원 1명이 핵심 스토리 수행 | D10과 제출 직전 |

단위 테스트 수·커버리지 비율을 성과 목표로 삼지 않는다. UI의 단순 스타일·그림 배치까지 테스트를 복제하지 않는다. 보상 중복·잘못된 방문·저장 실패·실제 제한 우회는 테스트 비용이 작은 단계에서 먼저 확인한다. 각 개발자의 검증 증거는 PR에 3~5줄로 남긴다.

## 9 2 자동 검증의 우선 대상

| 시험 ID | 입력과 조건 | 기대 결과 | 담당 |
|---|---|---|---|
| U01 | 동일 journeyId 2회, 다른 완료 뒤 과거 ID 반복 | 보상 효과 1회, 해당 원본 영수증 | B |
| U02 | 같은 날 DAILY 2개 | 성장 1회, 상한 유지 | B |
| U03 | 다른 날짜 DAILY, 성장 3 도달 | 최대 3, 이후 변화 없음 | B |
| U04 | 새 REGION과 같은 지역 재방문 | 최초 3개, 재방문 0개 | B |
| U05 | 소유하지 않은 의상·잘못된 슬롯 | 상태 보존, 오류 결과 | B |
| U06 | 저장 함수가 실패 | 성공 결과·브리핑 확정 없음 | B와 A |
| U07 | 거절·만료·철회 후 수락 도착 | 방문하지 않음 | C |

| U09 | UNKNOWN·RESTRICTED와 DEMO travelling | 조작 차단, 모의 상태가 우선하지 않음 | A |
| U10 | 경로 탐색 완료·경유지 도착 | 최종 완료 명령 없음 | A |

U01~06은 저장 트랜잭션 경계의 동작을 검증해야 한다. 계산 함수만 통과하고 실제 저장 연결에서 중복 지급되는 상태를 놓치지 않는다. DataStore 자체를 다시 테스트하기보다 앱이 한 번의 갱신 안에서 처리 목록·소유·영수증을 함께 바꾸는지 확인한다.

시스템 시험에서 실제 지원하지 않는 항목은 PASS로 쓰지 않고 NOT RUN 또는 BLOCKED와 이유를 남긴다. PC의 일반 에뮬레이터 통과를 Pleos 통과로 바꾸지 않는다. 가짜 제한 입력 시험과 실제 CarUxRestrictions 시험은 구별한다. 긴 전체 로그 대신 빌드 SHA·환경·단계·관측 결과·결함 링크를 기록한다.

## 9 4 인수 기준

PM과 교차 검토자 1명이 AC01 섬에서 의상 선택, AC02 DAILY 성장, AC03 새 지역 발견과 음식·의상·장식 사용, AC04 동행 외형 유지, AC05 방문 수락·거절·만료, AC06 재실행·중복 방지, AC07 실제·모의 범위 표시, AC08 release 설치·README 재현을 확인한다. 이 목록은 새 테스트를 무한 추가하는 절차가 아니라 제출 가능 여부를 판단하는 공통 기준이다.

치명 결함은 데이터 손상, 실제 제한 우회, 재현 가능한 앱 종료, 수락 없는 방문, 보상 반복 지급, APK 설치 불가다. 핵심 흐름을 막는 결함도 release 전 수정하거나 기능 경로를 제거·명시해야 한다. 작은 아트 어긋남·부가 문구는 알려진 한계로 남길 수 있다. 치명 결함을 보유한 상태에서 완성이라는 표현을 사용하지 않는다.

## 9 5 성능과 유지보수 목표

초기 개발 목표는 지정한 기준 PC에서 초기 화면 5초 이내, 짧은 조작 반응이 눈에 띄게 멈추지 않음, 10분 반복 시연에서 앱 종료 없음이다. 실측 전 수치이며 안전·품질 보증이 아니다. 차이가 있으면 장비·빌드·관측 시간을 기록한다. 60fps나 메모리 목표를 추정 수치로 홍보하지 않는다.

메인 스레드에서 파일·네트워크·큰 비트맵 디코딩을 직접 수행하지 않는다. 작은 로컬 자산을 쓰고 무한 애니메이션·고빈도 센서 수집을 피한다. 성능 문제가 생겼을 때에만 해당 구간을 프로파일링한다. 2주 동안 분산 추적·외부 분석 서버·지속 부하 시험 시스템은 만들지 않는다.

## 9 6 착수 개정본의 추가 결함 시험

| 시험 ID | 입력과 조건 | 기대 결과 | 담당 |
|---|---|---|---|
| U14 | 전체 초기화와 늦은 도착 콜백 경쟁 | 초기화 전 generation의 보상 재생성 없음 | A |
| U15 | 저장 실패 뒤 같은 도착 재시도 | 성공 때 한 번만 반영, ID 유지 | A와 B |
| U16 | 화면의 오래된 활성 버튼, 현재 gate 제한 | 서비스 호출 차단과 연출 중단 | A와 해당 UI |
| U17 | SDK 출처와 DEMO evidence 불일치 | 보상 거부, 상태 보존 | B |
| U18 | 브리핑 확인 저장 실패 | 성장 재지급 없음, 결과 재확인 가능 | A와 B |
| X01 | Windows clone·정적 검사·debug 빌드 | 경로·줄바꿈·SDK 설정 오류 구분 | A와 B |
| X02 | macOS clone·정적 검사·debug 빌드 | Windows와 같은 계약·콘텐츠 사용 | PM |
| X03 | Windows release APK를 기준 Pleos에 설치 | 실행·ABI·서명·기본 시연 확인 | A와 C |

출시 전 최소 연결 계약 시험은 I01, I02, I03, I05와 U14다. A가 fixture와 fake로 경계를 한 번 연결하고, 각 작성자가 자기 실패 분기를 책임진다. PM이 네 사람의 단위 시험을 다시 구현하지 않는다. 테스트 기록에는 OS·CPU·JDK·AVD·실행 명령·SHA를 적고, 수행하지 못한 항목은 NOT RUN 또는 BLOCKED로 남긴다.

정적 검사 명령은 `scripts/check_all.py`로 통합했다. 경로·카탈로그·UI 샘플·검증기 회귀 시험을 실행하며, Android 옵션을 명시해야 환경 기록 확인과 실제 Gradle 명령을 수행한다. OS별 전체 명령은 15장을 따른다. Python 검증기 통과는 Kotlin 도메인 규칙이나 SDK 동작의 통과가 아니다.
