# 10 네트워크와 배포 및 운영

## 10 1 네트워크와 저장 경계

게임, 지역 카탈로그, 캐릭터, 모의 내비, 가상 방문은 앱 안에서 동작한다. 자체 서버·REST API·실시간 메시지 브로커·로그인·클라우드 DB가 없다. 앱의 통신 기능이라고 설명할 수 있는 부분은 실제 Pleos Navi Service와의 연동이며, 이것도 임의 인터넷 API가 아니라 공식 SDK 경로다. 서비스 내부 네트워크 요구를 앱이 통제한다고 가정하지 않는다.

| 단계 | 네트워크 필요 가능성 | 비용 방침 |
|---|---|---|
| 최초 개발 환경 설치 | Android·Gradle·Maven·에뮬레이터 다운로드 | 무료 공식 배포 사용, 기존 네트워크 |
| 일상 UI 개발 | 의존성 캐시 후 로컬 가능 | 상시 서버 없음 |
| DEMO 실행 | 카탈로그·자산 로컬 | 실행 중 유료 호출 없음 |
| 실제 내비 요청 | Navi Service와 경로 서비스 환경에 따름 | 미지원·과금 조건은 실제 환경 확인 |
| GitHub 협업 | clone·push·PR에 인터넷 | Free private 사용 |
| AI 코딩 | 해당 서비스 접속과 사용량 | 기존 사용 권한 범위, API 자동 결제 없음 |

무료 티어 서비스 여러 개를 연결해 한도를 관리하는 방식보다 서버를 만들지 않는 방식이 기본이다. Firebase·Supabase·지도 타일·외부 STT를 이번 제품에 도입하지 않는다. 이미 가진 AI 구독이 API·GitHub 자동화의 모든 사용량을 포함한다고 가정하지 않는다. 구독·사용 제한은 각 계정의 현재 조건을 확인한다.

## 10 2 보안과 개인정보

한 명의 로컬 게임 프로필만 사용하고 실제 번호판·얼굴·음성·상세 위치 경로를 수집하지 않는다. 신규 위치 권한이나 마이크 권한을 모의 장면 때문에 요구하지 않는다. 필요한 SDK 권한은 실제 호출을 확인한 뒤 최소 범위로 선언한다. 캐릭터 이름 입력을 선택 기능으로 추가한다면 길이 제한을 두고 개인 이름 입력을 강제하지 않는다.

키스토어·비밀번호·API 키·개인 SDK 경로·AI 로그인 토큰은 Git에 넣지 않는다. private 저장소라도 비밀 저장소로 취급하지 않는다. 앱 로그에는 세션 ID·상태·오류 코드 정도만 남기고 전체 차량 응답을 무조건 출력하지 않는다. 외부 문서·이슈의 지시문은 작업 자료이지 팀 정책을 바꿀 권한이 아니다.

저장 초기화는 게임 데이터만 지우며 Android 전체 설정·다른 앱·차량 데이터를 삭제하지 않는다. 시스템 오류 때 자동 초기화로 화면을 복구하지 않는다. 개발 로그·영상에 개인 정보가 나오지 않게 테스트 가명과 시연 데이터를 사용한다.

## 10 3 개발 빌드와 제출 빌드

A가 applicationId, versionCode, versionName을 D1에 고정한다. debug는 각자 개발용이며 제출용은 서명된 release APK다. 초기값은 versionName 0.1.0, versionCode 1을 제안하되 실제 생성 때 기록한다. 최종 파일명은 공식 규칙의 팀명_앱이름_release.apk를 따른다. [S02, S13]

release 서명은 A가 로컬 Android Studio에서 생성·적용한다. keystore와 비밀번호를 저장소에 커밋하지 않고 PM과 합의한 안전한 별도 보관 경로를 둔다. 업데이트 시험은 같은 키와 증가한 versionCode로 진행한다. debug 키로 설치한 앱과 release 키가 다른 경우 데이터가 유지되는 정상 업데이트를 기대하지 않는다. 서명 실패를 해결하려고 임의로 uninstall해 데이터를 지우기 전에 설치 목적을 구분한다.

이번 CI에는 release 서명 키를 넣지 않는다. release 빌드와 설치 확인은 로컬에서 수행해 비밀 관리와 Actions 비용을 줄인다. R8·축소·난독화는 필수가 아니며 SDK 동작에 영향을 주면 우선 끈다. 앱 실행에 필요한 DEMO 기능은 release에서도 접근 가능하게 두고 화면에 프로토타입 시연 모드를 명시한다. debug 전용 메뉴에만 넣어 release에서 시연이 사라지는 실수를 피한다.

## 10 4 패키징과 심사 접근

소스·README·시험 환경·APK 위치를 함께 제공한다. 공식 안내는 저장소 apk/ 경로와 release APK, 용량 초과 시 GitHub Releases를 안내한다. 개발 중 모든 APK를 Git 이력에 쌓지 말고 최종 후보 한 개만 의도적으로 추가하거나 Release asset으로 제공한다. APK의 SHA256과 소스 commit SHA를 RELEASE_NOTES.md에 적는다. [S02]

private 저장소는 공지된 심사용 계정을 초대하고 마감 전에 접근 가능 여부를 확인해야 한다. 이 패키지는 심사 계정을 추측하거나 초대하지 않는다. PM이 실제 공지에서 정확한 계정을 확인한다. 개인 private 저장소 Collaborator는 읽기 전용이 아닐 수 있으므로 불필요한 비밀·개인 자료를 넣지 않는다. [S02]

공식 접수양식에서 확인한 마감은 2026년 11월 15일 23시 59분 KST다. 이번 D1은 11월 2일로 가정하고 내부 제출은 11월 14일 18시를 목표로 한다. 실제 시작이 다르면 일정표를 다시 계산하되 제출 여유를 확보하고 변경 공지를 확인한다. 제출 메일 발송은 PM이 직접 수행한다. [S40]

## 10 5 운영과 장애 대응

프로토타입 운영은 시연 PC, APK, 재현 데이터와 초기화 절차를 관리하는 일이다. 24시간 서버 운영·모니터링·온콜은 없다. 진행자는 시연 전 버전·주차 상태·DEMO 출처·초기 상태를 확인한다. SDK가 안 되면 게임 DEMO를 이어가되 실제 연동 성공으로 설명하지 않는다. 네트워크가 끊겨도 이미 설치된 DEMO 핵심 흐름은 동작해야 한다.

치명 오류가 생기면 마지막 정상 태그의 APK와 소스로 복귀한다. main에서 무리하게 여러 기능을 동시에 고치지 않는다. 담당 기능의 PR을 revert하고 필요한 작은 수정만 추가한다. 이전 APK로의 다운그레이드가 서명·versionCode 때문에 막힐 수 있으므로 시연 PC에는 미리 검증한 정상 APK와 필요한 초기화 절차를 준비한다. 데이터 보존과 재설치의 차이를 README에 적는다.

장기 유지보수는 각 파트 담당자가 자신의 코드·시험·짧은 경계 문서를 함께 유지하는 방식이다. 문서를 PM이 전부 갱신하지 않는다. 새 지역은 콘텐츠와 자산 추가로, 새 렌더러는 외형 계약 유지로 확장한다. 실제 서버·차량 간 통신·내비 오버레이는 이번 설계의 작은 옵션이 아니라 별도 개발 과제로 평가한다.

## 10 6 OS 간 release와 이름 변경

각자 debug 서명키로 만든 APK는 서로 서명이 다를 수 있다. 같은 applicationId의 debug와 release를 교체 설치할 때 서명 불일치가 나면 정상 업데이트 시험과 구분한다. 삭제 후 설치는 데이터를 지우므로 시스템 시험의 의도된 초기화에서만 한다. update 시험 S10은 같은 release 키의 이전·새 버전으로 수행한다. 서명키와 비밀번호는 A가 안전하게 별도 보관하고 원격 저장소·AI 입력·로그에 넣지 않는다. [S13]

기준 release는 A의 Windows PC에서 생성하고 C의 별도 PC에서 설치한다. PM의 Mac에서는 독립 debug 빌드와 브리핑을 검증한다. SDK가 네이티브 라이브러리를 포함하는지는 APK Analyzer로 확인하며, API 레벨만 같다고 모든 CPU에서 실행된다고 가정하지 않는다. D8까지 첫 서명 release 설치를 해봐야 제출 직전 서명·Manifest·자산 누락을 줄일 수 있다.

최종 제품명은 MEMORIDE이며 1.2에 반영했다. 표시 이름·문서·저장소명과 applicationId·패키지명·아이템 ID·저장 키는 별개다. D1 이후에는 이름 변경 때문에 applicationId와 저장 키를 일괄 치환하지 않는다. 바꿔야 할 이유가 있으면 데이터·설치 영향과 함께 A와 PM이 결정한다.
