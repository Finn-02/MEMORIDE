## 실제 실패 UI와 복구

전용 앱의 `files/datastore` 디렉터리 권한만 700→500으로 잠시 바꿔 쓰기 거부를 만들었다.
별도 가드는 최대5분 후 또는 완료 표시 즉시 finally에서700으로 복구하고 확인했다.
세 번 모두 복구 확인 완료이며 남아 있는 쓰기 거부 가드는 없다.
실제 전원 차단·저장 장치 고장 시험을 대신하지 않는다.

- 직전 APK의 도착 저장 실패: 실패 전후 파일 동일. 복구 후 재시도에서 원본1개만 추가되어 총2개/아이템6개.
- 직전 APK의 ack 실패: 브리핑과 재시도 버튼 유지, 성공처럼 이동하지 않음. 파일 동일.
  복구 후 재시도는 원본/아이템을 보존하고 pending만 지운 뒤 섬으로 이동.
- 이 과정에서 영어 오류 `Arrival could not be saved`가 노출되어 A 화면의 안내만 수정했다.
- 새 APK에 같은 쓰기 거부를 다시 적용해
  “도착 기록을 저장하지 못했어요. 다시 시도해 주세요.”와 재시도 버튼을 실제 확인했다.
  실패 전후 파일 SHA256 `bc3e3fe1366a6af5e92bbad1c686ed90afe404e0a0b0ece5e93a6c5919e8612b`로 동일.
- 복구 후 USER_CONFIRMED DAILY 재시도: 기존 대전 원본 보존, 새 원본1개만 추가,
  성장0→1·아이템3개 유지·시간/거리 null. 실제 브리핑에 사용자 확인 출처·성장0→1·추가 기념품 없음,
  측정 영역 생략을 확인했다. 닫기는 pending만 해제했다.

## 표시·환경 복구와 검증 한계

[이전 큰 글자/가로 인수](A06_USER_CONFIRMED_UI_LARGE_TEXT.md)의 전체 질문 스크롤 수정은 유지했다.
이번에는 방문의 요청/수락을 한 화면에서 확인하려고 Android 설정 UI에서 최소 화면 크기356dpi를 사용했다.
종료 시 UI로 기본420dpi·글자1.0·세로로 복구했고, 저장 폴더700과 섬 복귀를 확인했다.
TalkBack·모든 키보드 포커스·전체 화면 대비 등 포괄적 접근성 인수는 NOT RUN이다.

합성 기록을 분리하려고 보조 user10을 만들었으나 화면이 검게 남았다.
QEMU는 살아 있었고 guest power/display가 Asleep/OFF였으며 화면을 깨우지 못했다.
전용 guest를 재부팅해 user0으로 복귀했고 user0 저장 파일 해시 불변을 확인했다.
보조 user10은 미사용 상태로 남겼다. 이 현상을 앱/QEMU 크래시로 판정하지 않는다.
기존 Pleos QEMU의 c0000005 종료와 동일 원인이라는 근거도 없다.
