# 14 설계 검토와 착수 판단

## 14 1 대안 비교

| 선택지 | 장점 | 2주 MVP에서의 문제 | 판단 |
|---|---|---|---|
| Kotlin Compose 단일 앱 | Pleos와 같은 Android 환경, 하나의 APK | 팀이 Kotlin을 익혀야 함 | 기본안 |
| 웹 전용 목업 | UI 제작이 빠름 | 실제 Pleos 연동·APK 근거가 약함 | 보조 설명용만 |
| Unity 또는 3D 게임 | 풍부한 연출 | SDK 연결·빌드·자산 부담 증가 | 제외 |
| 서버와 실제 A·B 단말 | 실제 전달 증명 | 인증·네트워크·장비·운영 부담 | 제외 |
| 로컬 A·B 상태 머신 | 무료·재현 가능·동의 흐름 검증 | 실제 통신은 증명하지 못함 | MVP 기본안 |
| 다중 모듈·DI 프레임워크 | 경계를 기계적으로 강화 | 초기 설정·개념·빌드 복잡성 | 디렉터리 경계로 시작 |
| 화면만 분담 | 처음 배분이 쉬움 | 상태·저장·SDK를 여러 명이 수정 | 기능 소유권으로 대체 |

이 비교는 외부 실험으로 도출한 성능 순위가 아니라 팀의 기간·비용·장비 제약에 따른 설계 판단이다. 더 간단한 구조가 같은 인수 기준을 충족하면 담당자가 제안해 바꿀 수 있다.

## 14 2 결합도와 응집도 검토

B의 게임 상태와 보상·꾸미기를 함께 둔 것은 같은 불변 조건을 한 사람이 관리하게 하기 위해서다. C의 가상 방문은 보상이 없고 영구 저장도 필요하지 않아 독립 상태로 둔다. PM 브리핑은 상태를 표시하는 순수 화면으로 고정해 낮은 난이도의 실제 코드 작업을 맡긴다. A의 조립 코드는 화면 내부 규칙을 모르는 연결자로 남긴다.

파트 사이의 연결을 완전히 없앨 수는 없다. 공통 타입, 실제 제한 신호, 캐릭터 외형, 도착 결과의 네 연결은 사용자 경험의 일관성을 위해 필요하다. 이를 하나의 core/contract와 AppRoot로 모으고 샘플 입력을 제공해 대기 시간을 줄인다. 공용 계약을 거대한 공용 유틸 모음으로 키우지 않는다.

## 14 4 공식 평가 기준과 정직한 제출

공식 1차 기준은 차량특화성·창의성·기술 활용성·사업성이며 세부 배점은 공개되지 않았다. 따라서 이 명세에 자체 점수를 붙여 우승 확률처럼 쓰지 않는다. 차량 여정과 정차 맥락이 게임 변화에 연결되는 장면, 실제 SDK 사용 범위, 가족의 짧은 사용 경험, 지역 콘텐츠 확장 구조를 증거로 보여준다. [S01]

사업성은 현재 고객 수·매출·MAU가 있는 서비스처럼 쓰지 않는다. 초기 목표 고객과 반복 이용 가설을 제시하고 작은 사용성 관찰 결과만 실제 결과로 보고한다. 유료 제휴·수익모델은 후속 검토이며 무료 MVP에 광고·결제 코드를 추가하지 않는다. 방문 기능의 악용·주의 분산 가능성도 한계로 설명한다.

유사 차량 펫·지역 미션·소통 아이디어가 이미 공개된 이력이 있으므로 조합의 차별성을 구체적으로 설명하되 기존에 없다는 전수 검증 결과로 쓰지 않는다. 이번 문서는 특허 신규성 조사나 시장의 모든 프로젝트를 조사한 보고서가 아니다. 구현의 타당성과 제출 표현의 근거를 마련하는 개발 명세다.

## 14 5 첨부 강의 자료의 적용

| 자료와 전체 분량 | 검토 범위 | 이번 설계에 적용 | 직접 적용하지 않는 항목 |
|---|---|---|---|
| L01 웹서비스 기획 1, 45쪽 | 비즈니스 모델·시장·고객·여정 | 대상 가설, 기대효과, 대체재, 짧은 사용자 여정 | 시장 규모·수요·네트워크 효과의 추정 수치 |
| L02 웹서비스 기획 2, 25쪽 | UX·IA·와이어프레임·흐름·스토리보드 | 화면 ID, 통합 메뉴, 와이어프레임과 예외 | 전체 화면을 처음부터 완성 디자인하는 작업 |
| L03 웹서비스 기획 3, 49쪽 | A/B·프로토타입·MVP·PM·WBS·위험 | 작은 프로토타입, 역할 위임, 선행 관계, 위험·검증 | 소수 사용자 비교를 통계적 A/B 성과로 주장 |

강의의 원문·슬라이드 이미지·사례 그래프는 배포 ZIP에 재수록하지 않는다. 개념을 카일랜드 상황에 맞춰 새로 작성했다. 강의의 수식·사례·분류는 이 프로젝트의 실측 결과나 표준 요구사항이 아니다. UI와 UX, 경로 탐색과 주행 완료, 목업과 실제 SDK 시험을 문맥에 맞게 구분한다.

## 14 6 지금 결정된 것과 D1에 확인할 것

결정된 것은 제품 정체성, 2:2:2:1 개발 노력 목표, 기능 소유권, 단일 앱·로컬 데이터, 공통 계약, DEMO 출처, 실제 제한 우선, 작은 PR과 수동 Actions다. 시작 전에 PM이 모든 함수·클래스·픽셀을 설계할 필요는 없다.

D1에는 실제 가용 시간, 팀원 역할·GitHub ID, 실행 가능한 PC와 백업, 호환 도구 버전, 빈 앱 빌드, 공통 타입 컴파일을 확인한다. D2에는 SDK 호출·권한·제한 상태의 관측 결과를 기록한다. 이 사실 확인 전에는 구동 보장·일정 보장·무결함·주행 안전 인증을 선언하지 않는다. 결함을 조기에 발견하고 줄일 수 있는 구조라는 범위에서 이 명세를 사용한다.

## 14 7 이번 개정에 적용한 분석과 실제 수정

모든 분석 기법을 이름만 나열하지 않고 이번 결함을 찾는 데 필요한 방법을 적용했다. 수치는 실측하지 않았으며 FMEA는 정성 우선순위로 사용한다. 보안·형상·문서 절차를 별도 시스템으로 늘리지 않는다.

| 분석 방법 | 찾은 문제 | 적용한 조치 |
|---|---|---|
| 기능 응집도와 의존성 그래프 | B 렌더러와 SDK 대기로 UI 정지 | 순수 화면·슬롯·UI 샘플, A01 조기 공유 |
| 상태 전이·사건 순서 | 경로 완료와 도착 혼동, 취소 뒤 콜백 | source·revision·generation 검사 |
| 결정표·불변 조건 | 같은 날·같은 지역·같은 ID 지급 혼동 | DAILY/REGION 분리, 원본 영수증 맵 |
| 동시성·실패 주입 사고 실험 | 초기화 뒤 늦은 쓰기, 저장 실패 retry | 조정 경로·세대 무효화·동일 명령 재시도 |
| 경계값·동등 분할 | null을 0, NaN·음수·bool 혼용 | 데이터 검증과 U12/U17 |
| 요구사항 추적 | 화면만 완료하고 설치·동의 누락 | F/U/I/S/AC 연결과 X01~03 |
| OS 실패 분석 | JDK·ABI·줄바꿈·경로 차이 | OS 안내·toolchain 기록·doctor·경로 검사 |
| 비용과 최소 권한 검토 | 개인 계정 다른 저장소 과금 혼입 | 저장소 Actions 우선 비활성, 수동 1 job |

## 14 8 FMEA 방식의 우선 위험

| 위험 ID와 우선도 | 실패 형태 | 예방과 탐지 | 남는 한계 |
|---|---|---|---|
| R01 높음 | SDK·주차 입력 미확인 | D1~2 spike, UNKNOWN 차단 | 실제 연동은 실행 전 보장 못 함 |
| R02 높음 | 반복 보상·부분 저장 | 단일 edit, 원본 영수증, U01 U06 | 장기 이력 보존은 후속 설계 |
| R03 높음 | reset 뒤 늦은 입력 | generation·직렬화·U14 | 프로세스 밖 이벤트 복원 제외 |
| R04 높음 | 제한 중 조작·연출 | 최신 gate 재확인·화면 이탈 중단 | 실제 주행 안전성은 별도 검증 |
| R05 높음 | 수락 없는 방문 | 요청 ID·단조 시계·U07 U08 | 실제 원격 전송의 동의 증명 아님 |
| R06 높음 | A/B 작업 과부하 | D3 D7 분담 조정·기능 수 축소 | 실제 숙련도·가용 시간 미측정 |
| R07 중간 | OS·JDK·파일 경로 실패 | toolchain·wrapper·X01 X02 | 도구 설치와 장비 가상화는 각자 확인 |
| R08 높음 | release 서명·APK 설치 실패 | D8 첫 release·C PC 설치 | 실제 서명은 A가 수행해야 함 |
| R09 중간 | AI가 공통 코드 변경 | 작은 AGENTS·역할·PR diff | 지침은 강제 접근 제어가 아님 |
| R10 높음 | 자동 CI 비용 증가 | repo Actions 비활성·수동·예산 확인 | 계정 설정은 실제 소유자 확인 |
| R11 중간 | 시연과 제출 설명 불일치 | 실제·DEMO 표기·동일 SHA | 가상 결과는 SDK 성공 증거 아님 |
| R12 높음 | 제출 파일·권한·동의 누락 | D13 내부 제출·인수표 | 심사 계정·마감 시각 최종 확인 필요 |

가능성과 영향의 수치 곱을 우승 확률이나 안전 등급처럼 쓰지 않는다. 가장 큰 남은 불확실성은 팀 장비의 실제 Pleos 실행, SDK 도착 식별, 주차 입력, 개발 가용 시간이다. 이들은 문서를 더 길게 쓰기보다 첫 이틀의 실행으로 줄인다.

## 14 9 최소 보안과 확인 절차

로그인·결제·백엔드·실차 번호판·위치 이력·외부 메시지 저장을 만들지 않아 데이터와 네트워크 표면을 줄인다. 비밀·서명키·동의서는 저장소와 AI 입력에서 제외한다. PR 하나와 관련 시험, 큰 그림 변경만 PM 검토로 충분하다. 보안 도구·서명 워크플로·다중 승인·서비스 계약서를 별도 개발하지 않는다.

개발 착수 가능 판정은 조건부다. 설계·샘플·정적 도구는 준비했지만, 앱·SDK·양 OS 빌드가 통과한 상태는 아니다. D1 A01을 확인하면 병렬 개발을 시작하고, D2 결과에 따라 SDK 설명과 구현 범위를 정직하게 조정한다. 고정된 제품 컨셉을 유지하면서도 기능 수와 연출은 줄일 수 있다.
