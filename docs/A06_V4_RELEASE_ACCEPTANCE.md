## 아티팩트와 완료 범위

## 최신 v4 Pleos P/D/P

공식 Pleos2.1/API34/x86_64, Pleos_Connect_v2_0, Emulator37.2.13, 실제 RAM4096, SwiftShader/Vulkan disabled/headless/cold boot/no snapshot으로 별도 AVD에서 시행했다. 설치 이미지 package.xml revision2/source.properties revision1을 구분했다.

실제 user10에서 최초 설치/정식 Main을 실행했고 설치 base.apk SHA도 위 전달본과 일치했다.
P의 DO=false/UxR0·섬 표시 → 사용자 공식 콘솔 수동 D의 DO=true/UxR80·플랫폼 ‘주행 중에는 사용할 수 없습니다’ → 사용자 수동 P의 섬 복귀/인벤토리 실제 조작을 확인했다.
D 첫/마지막 host 표본 간140.841504초, P복귀 후 표본 간78.718704초이며 앱PID는 동일했다. 정확한 기어 입력 시각/연속 텔레메트리가 아니다.
이 기능 관측 중 호스트 종료는 없었으며, 이후 AVD 종료 요청 때의 오류는 아래 별도 기록이다. 1회 결과로 장시간 안정성·실차·주행 안전을 인증하지 않는다. Release gate 태그 로그는 비어 있어 내부 gate-log PASS를 주장하지 않는다.

## 최신 Release 핵심 시연 3회

종료 오류 후 복구한 전용 합성 기록 AVD에서 공개 DEMO 전체 초기화→D03 목적지 요청→READY 확인→모의 출발→완료/저장→브리핑→빵모자 장착/모모 선택→동행 외형→가상 양측을 도구로 조작한 방문 요청/수락/닫기→섬→실제 프로세스 재실행을 총3회 수행했다. 각 회차 초기화 후 기본 토리·대전 최초 발견·기념품3종이 다시 확인되고, 방문 전후 섬 문자열과 재실행 후 외형/성장0이 일치했다. 사용자 실제 동의나 실차 방문 인증으로 설명하지 않는다.

여정ID는 `29eb774b-b28e-4d43-9766-ae5741035dec`, `e257853b-fa54-49da-8907-49065b76c812`, `ea0d035d-457f-4f8e-8869-9939029936df`로 모두 달랐다. 첫 회차는 D04 replay의 ‘같은 원본 영수증과 새 지급0’ 표시도 확인했고, 배경→전경 복귀에서 동일PID/섬 문자열 보존을 확인했다.

2회차 첫 입력 전 UI dump에서 앱 노드가 없어 입력을 중단했다. 당시 화면은 UNKNOWN 차단이며 PID는 살아 있었다. 정식 Main 재진입 후 실제 P와 활성 앱 UI를 확인하고 진행했다. 동행 버튼이 화면 아래로 잘려 보이지 않았던 도구 실패는 현재 XML의 스크롤 영역을 스크롤한 뒤 재조회해 이어갔으며, 2회차 저장·초기화를 다시 실행하거나 실패 시도를 별도 성공 회차로 세지 않았다. 차량 gate를 주입하거나 UNKNOWN을 임의로 해제하지 않았다.

이 결과는 지정 핵심 스토리의 S09 반복 근거다. D01~D06 전체를 각3회, 모든 경쟁 조건·옛 token 재전달·전체 접근성/기기 전수 또는 C05 전체 완료로 확대하지 않는다.

## 추가 Release 방문 분기

실제 P 허용 상태에서 도구로 가상 양측을 조작해 거절, 실제17초 대기 뒤 만료, 요청 철회, 수락 후 캐릭터 숨김/다시 표시/닫기, 요청 중 USER_CONFIRMED 모드 전환→DEMO 복귀의 종료/자동 비재개를 각각 확인했다. 거절·만료·철회·모드 종료에는 방문 캐릭터 표시 제어가 없고, 수락 후에만 캐릭터를 관찰했다. 전후 모모/빵모자·성장0/섬 문자열도 일치했다.

독립 사례 사이에는 공개 ‘방문만 다시 준비’를 사용했다. 따라서30초 쿨다운 통과나 raw 저장 파일SHA/모든 보상 수량 불변을 주장하지 않는다. 동의는 이 개념 시뮬레이션의 가상 역할 입력이며 실제 다른 사람이나 차량의 동의/통신이 아니다. 활성 방문/reset 경쟁과 늦은 token 기기 재주입·D 중 방문 전 조합은 NOT RUN이다.

## 종료 오류 조사와 복구

기존 D 조건의 `c0000005`는 [이전 조사](A06_DRIVE_CRASH_INVESTIGATION.md)와 C의 첫 실패/한 차례 대조 재시도 통과로 유지한다. C 고정 `685d107` debug APK의 Vulkan-off 대조는 아직 남아 있다. 최신 v4 기능 시험이나 C의 일반 API37 설치를 그 대조로 세지 않는다.

추가로 headless QEMU 종료 요청 구간의 `combase.dll / c0000602`를2회 관측했다.
- 15:49:15.974 KST 종료 ACK 뒤15:49:18.254 Event1000/PID44824, reportId `0eae368d-c86a-4b77-bf05-e8100089d516`.
- 다른 합성 저장 AVD에서 앱 force-stop/PID없음을 확인한 종료 요청 뒤16:07:36.729 Event1000/PID8916, reportId `c12ebf6c-3aaa-4dca-a53a-c2a55e5a24dc`.
- 각 오류의 Event1000 하나/1001 두 개는 같은 reportId다. 이벤트3개를 크래시3회로 세지 않는다.
- 첫 기존 dump의 예외 모듈/오프셋은 `combase.dll+0x8f722`, exception `c0000602`로 WER와 일치했다. 로컬 보관 dump의 구조·모듈·코드 주소 후보만 확인했으며 원시 dump를 전달하지 않는다.
- 스택 주소 후보는 심볼 기반 unwind가 아니므로 함수 호출 관계나 오디오/그래픽/COM의 근본 원인을 확정하지 않는다. 기록된 cdb 경로의 디버거를 찾지 못했으며 심볼 기반 분석은 NOT RUN이다.
- Microsoft의 [NTSTATUS 정의](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55)는 `c0000602`를 fail-fast 예외로 정의한다. 코드의 의미가 특정 원인을 입증하지는 않는다.

두 번째 관측으로 현재 앱 실행이 종료 오류의 필수조건은 아니지만 이전 앱 영향/앱 무관성 전체를 배제하지는 않는다. 다른 AVD 관측이므로 통제된 인과 실험 전체로 주장하지 않는다. 종료 오류 반복은 중단했고 앱/저장/제한·SDK/드라이버·보안 설정을 바꾸지 않았다.
첫 종료 오류가 났던 v4 AVD를 wipe 없이 재부팅해 기존 모모/빵모자/성장0·ack 완료 섬 문자열이 이전 기록과 일치하는 것을 확인했다. 전체 저장 바이트 무결성 시험은 아니다.

## 남은 인수와 책임

- C: 복귀 후 기존 비교 AVD/고정685d107 APK의 Vulkan-off 앱 미실행 대조1회, 통과하면 같은 조건 앱 실행3회. 첫 이상에서 중단. 최신 v4 재설치나 기본 조건 자동 재시도 없음.
- A: PM 요청에 따라 PR 본문과 README에 검증 결과·A06/A05 빌드 구분을 반영하고, 문서만 변경됐음을 확인한 뒤 PR을 Ready로 전환한다. 병합은 수행하지 않는다.
- PM 회신 기준 C의 Vulkan-off 비교는 최종 시연 환경을 확정할 때 별도로 확인한다. 서명 v4 교차 설치 검증과 구분한다.
- PM: 위 기능 근거와 미해결 환경 오류를 보고 PR 병합 및 최종 시연 환경/제출 여부 판단. 근본 원인 완전 규명을 새 PM 병합 필수조건으로 임의 추가하지 않는다.
- 실차/ARM/실제 PLEOS 자동 최종도착·물리 전원/저장장치 고장·다운그레이드 전수·전체 접근성/기기 경쟁 조건은 NOT RUN이다. 자동 도착 기능을 구현·인증했다고 설명하지 않는다.
