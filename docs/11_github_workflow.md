# 11 GitHub private 협업과 Actions 절약

## 11 1 저장소와 최소 권한

PM이 private 저장소 하나를 만들고 A·B·C를 초대한다. 기본 브랜치는 main, 검토 단위는 작은 PR이다. 유료 플랜을 새로 구매하지 않는다. GitHub Free private에서 강제 브랜치 보호나 Code owners가 제공된다고 가정하지 않는다. 사용 중인 계정이 지원하면 main 직접 push·force push·삭제를 막고 리뷰 1개를 요구한다. 지원하지 않으면 같은 규칙을 팀 합의로 운영하며 강제 보안 기능이라고 표현하지 않는다. [S14, S15]

일반 개발자는 part 브랜치에만 push한다. PM 또는 A의 최초 부트스트랩 커밋만 빈 main에 직접 올릴 수 있다. 이후 main은 검토된 PR로 통합한다. 기본 검토 짝 A↔PM, B↔C를 쓰고 계약에 영향을 받는 소비자 한 명만 필요할 때 추가한다. 모든 변경에 전원·PM 승인을 요구하지 않는다.

## 11 2 브랜치의 짧은 수명

브랜치는 `part/a-journey-01`, `part/b-island-01`, `part/c-visit-01`, `part/pm-briefing-01`처럼 작업 단위로 만든다. 파트 하나의 전체 개발을 담는 2주짜리 브랜치나 별도 develop은 만들지 않는다. D3부터 작은 PR을 main에 병합한다. 작동하지 않는 기능은 숨겨 기본 실행 경로를 유지한다.

```bash
git switch main
git pull --ff-only
git switch -c part/b-island-01
```

공유 main을 반영할 때는 `git fetch origin` 후 자기 브랜치에서 `git merge origin/main`을 사용한다. 초보 팀의 기본 절차에서는 rebase와 force push를 요구하지 않는다. 충돌이 생기면 작성자가 자기 변경의 의도를 확인해 해결한다. 다른 사람의 코드를 통째로 덮어써 해결하지 않는다.

PR은 squash merge하고 완료 브랜치를 삭제한다. 다음 작업은 최신 main에서 새 브랜치를 만든다. 작업 중인 변경이 있으면 main 전환부터 강행하지 말고 별도 작업 커밋 또는 임시 보관 후 상태를 확인한다. 파괴적인 reset·clean·이력 재작성은 일반 절차에 넣지 않는다. 잘못 병합한 커밋은 revert PR로 되돌리고 공유 이력을 유지한다.

## 11 3 Actions를 쓰지 않아도 완료 가능한 개발

이 팀의 기본은 로컬 검증이며 새 저장소의 Actions는 처음에는 Disable로 둔다. 설정 위치는 저장소 Settings → Actions → General이다. 이 설정은 해당 저장소에 적용하고 다른 연구 저장소의 워크플로·결제·카드 설정은 건드리지 않는다. [S33]

필요할 때만 PM이 이 저장소의 Actions 사용을 허용하고 제공 수동 workflow를 실행한다. 요금은 저장소 소유자의 계정 사용량에 영향을 받으며, 다른 저장소에서 포함량을 사용했을 수 있다. 알림 예산은 자동 차단과 다르다. 공식 안내가 제공하는 저장소 범위 예산과 Stop usage 옵션을 현재 계정에서 확인하되, 추가 과금 0을 확인할 수 없으면 실행하지 않고 로컬 결과를 제출한다. 포함 minutes를 새 저장소 전용 무료분으로 계산하지 않는다. [S16, S17, S34]

## 11 4 제공 workflow의 비용 제어

`.github/workflows/manual-check.yml`은 workflow_dispatch만 있고 push·PR·schedule 트리거가 없다. job은 Ubuntu 한 개, 전체 시간 제한 15분이다. 기본은 정적 검사이며 Android 옵션을 켜면 환경 기록 확인, Java 설정, 같은 로컬 Gradle 검사를 순서대로 실행한다. emulator·Mac·Windows 행렬·서명·배포·AI API·artifact 업로드·원격 cache는 없다. 같은 브랜치 재실행은 이전 실행을 취소하도록 설정한다. [S23]

환경이 미확정이면 JDK 설치와 Android 빌드를 시작하기 전에 실패한다. SDK 저장소 접근 오류가 나면 실패 이유를 수정한 뒤 한 번만 재시도하며, 성공할 때까지 반복 실행하지 않는다. CI용 key를 새로 만들거나 실제 앱 비밀 값을 runner에 추가하지 않는다. 로컬에서 수십 번 반복할 작은 수정마다 Actions를 실행하지 않는다.

수동 workflow는 기본 브랜치에 있어야 Actions UI에서 발견된다. PR의 Actions가 돌지 않아도 정상이다. 수동 검사를 PR 필수 status check로 지정하면 대기가 생길 수 있으므로 이 MVP에서는 강제 필수 검사로 연결하지 않는다. YAML 정적 검사 통과를 GitHub 실제 실행 성공으로 기록하지 않는다.

## 11 5 AI와 병합

한 작업 트리에는 한 구현 세션을 사용한다. Codex와 Claude를 같은 폴더에서 동시에 수정하게 하지 않는다. 모델을 교대하면 git diff와 3줄 인계를 남긴다. GitHub 자동 AI 리뷰·클라우드 에이전트·API 키 기반 봇은 기본 사용하지 않는다. 사용 권한이 있는 기존 구독의 포함량 안에서 로컬 구현과 제한된 리뷰에 사용한다.

PR에는 작업 ID, 변경 행동, 계약 영향, 실제 로컬 명령과 결과, 미실행 항목만 적는다. 검토자는 위험한 경계 위주로 확인한다. 무조건 두 모델에게 전체 저장소를 재검토시키지 않는다. AI 제안이 다른 파트의 API를 바꾸면 현재 계약을 우선하고 필요한 변경만 요청한다.

## 11 6 최종 main과 제출

D11 기능 동결 후 최종 검증된 main 커밋에 태그를 붙인다. APK·문서·영상은 그 SHA와 일치하게 만든다. APK는 최종 파일만 apk 폴더에 명시적으로 추가하고 서명키는 제외한다. 용량이 크면 공식 제출 안내대로 GitHub Releases를 사용한다. private 심사용 계정은 공지에서 정확히 확인한 뒤 초대하고 접근을 점검한다. 코드·APK 열람에 필요한 접근만 설정하며 개인 저장소 collaborator의 쓰기 권한 특성도 확인한다. [S02]
