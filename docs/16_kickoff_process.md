# 16 개발 착수부터 제출까지의 흐름

## 16 1 시작 날짜와 제출 여유

D1은 2026-11-02 시작을 가정한다. 공식 마감일은 11-15이며, 팀 내부 제출 목표는 11-14 18시 KST다. 공개 HTML 일정은 날짜만 안내하지만, 11월 1일 내려받은 공식 접수양식에서 11월 15일 23시 59분을 확인했다. 시간대는 사이트 일정의 KST 기준을 따른다. 실제 시작이 달라지면 PM은 날짜를 조정하되 내부 제출 여유를 먼저 확보한다. [S02, S31, S40]

계획 노력은 A·B·C 각 약 30시간, PM 개발 약 15시간을 초기 가정으로 삼는다. 관리·자료 작성은 PM 개발 시간 밖이다. 이것은 팀원의 실제 가용 시간을 측정한 값이 아니므로 시작할 때 각자가 가능 시간을 알리고, 부족하면 D3 이전에 자산·추가 연출을 줄인다. 포인트는 시간 보장이 아니다.

## 16 3 하루의 작은 개발 순환

main 최신화, 자기 part 브랜치 생성, 역할 카드의 다음 작은 작업 선택, 필요한 파일만 읽기, 구현, 관련 로컬 시험, PR과 교차 검토, main 병합 순서다. 작업 시작과 종료에 git status를 확인한다. 자기 폴더 내부 결정은 승인 없이 진행한다. 공용 타입 변경은 생산자·소비자 간 의미 확인 한 번으로 처리한다.

PR 설명에는 바뀐 행동, 계약 영향, 실행한 명령과 결과, 남은 제한만 적는다. 기능이 불완전해도 정상 컴파일되고 기본 경로를 깨지 않는 작은 기능 조각은 통합할 수 있다. 미구현 기능은 숨기거나 준비 중으로 표시하며 성공한 것처럼 표시하지 않는다. 하루 한 번 `docs/status/` 자기 파일에 오늘 결과·막힘·다음 작업을 3줄로 남긴다.

기본 리뷰 짝은 A와 PM, B와 C다. PM은 보상·동시성 전문 리뷰를 혼자 맡지 않는다. B가 A의 도착 연결, A가 B의 저장 경계를 필요한 PR에서 추가로 확인한다. 전원 승인을 요구하지 않는다. 검토자는 코드 전부를 이해하려 하기보다 변경된 경계·테스트·범위를 확인한다.

## 16 4 네 파트의 개발 순서

A는 공통 앱과 DTO를 먼저 공유하고 fake 여정을 연결한다. 이어서 SDK 변환·실제 gate·초기화·도착 연결을 만들고 release를 설치한다. B는 화면보다 상태와 보상·저장 규칙부터 만들고, 섬·아이템·렌더러를 붙인다. C는 가상 방문 상태를 네트워크 없이 만들고 동행·월드맵·Runner를 붙인다. PM은 샘플 결과의 브리핑부터 만든 뒤 콘텐츠와 실제 결과·예외 표시를 검증한다.

각 역할의 세부 작업 ID, 첫 입력, 완료 조건, 테스트는 `roles/`와 `tasks/backlog.md`가 기준이다. 소규모 함수·클래스·화면 내부 설계까지 PM이 대신 정하지 않는다. 큰 그림을 바꾸지 않는 더 쉬운 구현은 담당자가 채택하고 변경 이유를 PR 한 줄로 남긴다.

## 16 5 제출 가능 여부

한 캐릭터·한 지역으로도 선택, 모의 동행, 완료 저장, 브리핑, 기념품 사용, 동의 방문이 연결되면 핵심 흐름의 기반이 생긴다. 이후 자산을 확장한다. 일정이 부족하면 추가 표정·지역 수·세부 장식·자동 재생을 줄인다. 소유 검증·중복 방지·동의·출처·실제 제한을 줄여 일정만 맞추지 않는다.

서명 release 설치, 핵심 흐름 3회 반복, 재실행 복원, 같은 도착 반복, 방문 거절·만료, 실제·모의 범위 일치, private 심사 접근, README·영상·기획서·APK의 같은 범위를 확인한다. 공식 제출 요구와 팀 품질 기준은 `docs/contest_site_review.md`에서 구분한다. 전체 정적 도구 통과만으로 제출 앱 완성을 선언하지 않는다.

## 16 6 공식 양식과 내부 자료의 분리

공식 양식의 운영용 참가 정보와 심사용 작품 소개를 분리한다. 심사용 소개에는 개발자 실명·소속·연락처를 넣지 않는다. 내부 명세·역할 카드에는 담당자 정보가 있을 수 있으므로 그대로 제출 자료에 첨부하지 않는다. 공개 링크·화면·녹화의 계정·개인정보 노출을 점검하되 Git 이력을 임의로 다시 쓰거나 허위 작성자로 바꾸지 않는다. 양식 작성 방향은 templates/application_writing_guide.md를 참고한다. [S40]


제품명은 MEMORIDE로 확정됐다. 파트 번호는 1=A, 2=B, 3=C이며 배정만 config/team.json에서 완료한다. 실제 저장소 반영 여부와 기준 커밋은 REPOSITORY_STATUS.md에 기록한다.
